# check_mpic.sh スクリプトマニュアル

[![test](https://github.com/letticia/UPKI_Check_MPIC/actions/workflows/test.yml/badge.svg)](https://github.com/letticia/UPKI_Check_MPIC/actions/workflows/test.yml)

## 概要
`check_mpic.sh` は、指定されたFQDN（完全修飾ドメイン名）に対して、証明書発行に必要となる **CAAレコード** と関連する **CNAMEレコード** の設定状況をDNSを遡りながら確認し、さらに複数のパブリックDNSからの名前解決結果を照合することで **MPIC (Multi-Perspective Issuance Corroboration)** の要件を満たしているかを自動的にチェックするシェルスクリプトです。

各種SSL/TLSサーバー証明書の発行に際して、CAAレコードの不備や意図しないCNAMEチェーン、GeoIP制限やスプリットホライズン等に起因するMPIC検証エラー（海外からの名前解決失敗など）のトラブルシューティング・事前確認に役立ちます。

---

## 主な機能と挙動

1. **基本のレコード確認**
   対象のFQDNについて、`CAA` レコードと `CNAME` レコードを引き、その内容を出力します。
   - CAAレコードが見つからない場合は「CAAレコードがありません」と出力されます。
   - CNAMEレコードが見つからない場合は「CNAMEレコードがありません」と出力されます。

2. **CNAMEの自動追跡（チェーン解決）**
   対象のFQDNにCNAMEレコードが設定されている場合、その**参照先（CNAME先のFQDN）**に対しても自動的にCAAとCNAMEの確認を行います。
   この処理は、最終的にCNAMEの参照先がなくなる（Aレコード等の実体ドメインに落ち着く）まで繰り返されます。
   *(※ 無限ループを防ぐため、一度確認したFQDNに再度アクセスした場合はループを自動で検知し追跡を停止します)*

3. **名前解決の可否判定**
   `dig` コマンドで `NXDOMAIN`（ドメインが存在しない）または `SERVFAIL`（DNSサーバー側のエラー）が返ってきた場合、名前解決ができない旨を出力し、そのFQDNの確認を中断します。
   この2つは発行方式への影響が異なるため、分けて説明を出力します。
   - `NXDOMAIN` … **ACMEは発行不可、CSRは上位ADN次第**（後述「発行方式（CSR / ACME）による違い」を参照）
   - `SERVFAIL` … CAAレコードの確認結果も不明になるため、**どちらの方式でも発行不可**
     - SERVFAILの場合は、署名の検証を省く `+cd`（Checking Disabled）を付けて問い合わせ直し、解決できれば **DNSSECの検証失敗** が原因と表示します（後述「DNSSECの確認」を参照）。

4. **特定CA（認証局）の許可チェック（階層ごとの参考表示）**
   確認した各階層（対象FQDN・CNAME先・遡り先の親ドメイン）で取得したCAAレコードが `secomtrust.net` による発行を許可していない場合、その理由とともに警告を出力します。許可の判定方法は後述の「CAAレコードの許可判定」を参照してください。
   * ※ これは各階層単独の情報表示であり、そのCAAが実際に証明書発行へ影響するか（＝実効CAAかどうか）は後述の「実効CAAレコードの判定」およびMPIC判定結果を参照してください。
   * ※ CNAMEが張られたドメインでは、CAAの問い合わせ結果は参照先のものになるため、参照先の確認結果として表示します。

5. **実効CAAレコードの判定（MPIC判定に使用）**
   CAAレコードの仕様（RFC 8659 3節）に沿い、対象FQDNからラベルを1つずつ削って親ドメインへ遡り、**最初に見つかった空でないCAAレコードセット**のみを実効CAAとして採用します。実効CAAが見つかった時点でそれより上位のドメインのCAAは参照しません。
   - 各ドメインのCAAの問い合わせではCNAMEがたどられるため、**CNAMEの参照先に置かれたCAAも対象**になります（例: `www.example.ac.jp(CNAME先: cdn.example.net)`）。
   - ただし見つからなかったときに遡るのは**元のドメインの親**であり、CNAMEの参照先の親ドメインは探しません。参照先の親まで遡るのは旧仕様（RFC 6844）の動作で、RFC 8659 で廃止されました。CDN配下のホストでは、CDN側の無関係なドメインのCAAではなく、機関側の親ドメインのCAAが効きます。
   - 遡りは RFC 8659 どおりDNSルートの直前（TLD）まで行います（後述の「eTLD+1への遡り」はADN候補の表示用で、CAAの探索はそれより上位の `ac.jp` や `jp` も含みます）。

   実効CAAが `secomtrust.net` による発行を許可していない場合にのみ、MPIC判定結果を不合格とします（＝対象FQDN自身に許可CAAがあれば、無関係な親ドメインの制限的なCAAによって誤って不合格になることはありません）。

   **CAAレコードの許可判定**（RFC 8659 4節）
   - `issue` タグの値の発行者ドメイン名（`;` より前）が `secomtrust.net` と一致するものがあれば許可とします。大文字小文字は区別しません。
   - `issue` タグが1つもなければ、発行は制限されません。
   - `iodef`（違反の報告先）や `issuewild`（ワイルドカード証明書用）に `secomtrust.net` があっても、通常の証明書の許可にはなりません。UPKIではワイルドカード証明書を申請できないため、`issuewild` は判定に使いません。
   - `issue ";"` はすべてのCAの発行を禁止します。
   - critical フラグ（128）付きの未知のタグがあると、CAは発行できません。
   - `issue` の値に続く RFC 8657 のパラメータ（`accounturi` / `validationmethods`）は、許可の判定とは別に確認します（次の「CAAのパラメータ」を参照）。

   **CAAのパラメータ（RFC 8657、BR 4.2.2.1.2）**
   SC-098 により、**2027-03-15 から**CAは `issue` に付いた `accounturi`（発行できるアカウントの限定）と `validationmethods`（使える検証方式の限定）の処理が必須になります。
   実効CAAの `issue "secomtrust.net; ..."` にこれらのパラメータがある場合、次のように扱います。

   | 条件 | ACME発行 | CSR申請 |
   |---|---|---|
   | パラメータのない `issue "secomtrust.net"` も別にある | 影響なし | 影響なし |
   | `validationmethods` にUPKIのACMEで使える方式（`dns-01` / `http-01`、または同じ方式を表す `ca-tbr-7` / `ca-tbr-19`）がない | ❌ | ― |
   | `validationmethods` にACMEの方式がある | 使える方式を【注意】で表示 | ― |
   | `validationmethods` がある | ― | ⚠️ 要確認 |
   | `accounturi` がある | 指定されたアカウントを【注意】で表示 | ⚠️ 要確認 |

   - **2027-03-15 より前は判定に反映せず**、施行日以降に起きることを【注意】として表示します（終了コードは 1）。
   - CSR申請を「要確認」とするのは、UPKIのCSR申請でCAが使う検証方式（BR 3.2.2.4 の項番号。`validationmethods` では `ca-tbr-N` と書く）や、ACME以外の申請での `accounturi` の形式を、このツールでは判定できないためです。UPKI/CAに確認してください。
   - UPKIのACMEでは `tls-alpn-01`（`ca-tbr-20`）が使えないため、`validationmethods` がこれだけを許可している場合もACMEでは発行できないと判定します。
   - 施行日以降は、`validationmethods` で許可された方式だけを、後述の「ACME向けの事前確認」の判定に使います。
   - ACMEの方式を `ca-tbr-N` の形でしか書いていない場合は、ACMEの方式名（`dns-01` など）も併記するよう【注意】を表示します。BRは同じ方式を表すどちらの書き方も許可するよう推奨（SHOULD）していますが、必須ではないためです。
   - BRでは小文字が正式な表記ですが、CAが大文字小文字を区別しない照合をしてもよいため、このツールでは区別せずに扱います。
   - `accounturi` がUPKIで払い出されたACMEアカウントのURLと一致するかは確認していません。

6. **eTLD+1への遡り（Public Suffix List連携）**
   各種レコードの有無にかかわらず、サブドメイン（例: `sub.example.co.jp`）が指定された場合、そのドメインの所属するゾーンの頂点・ベースドメイン（eTLD+1 相当、例: `example.co.jp`）に到達するまで、ドメインラベルを1つずつ削りながら親ドメイン側へと遡って確認を繰り返します。
   * ※ 遡りの終点（eTLD+1）を正確に判定するため、初回実行時に Mozilla の **Public Suffix List (`public_suffix_list.dat`)** を公式から自動でダウンロードします。30日より古くなると自動で取り直します（後述「Public Suffix List (PSL) について」を参照）。

7. **代替DNSサーバー（8.8.8.8 / 1.1.1.1）での確認とMPIC判定**
   ローカル（デフォルト）のDNSサーバーでの一連の確認（遡り処理含む）が完了した後、指定された最初の「ターゲットFQDN」に対してのみ、以下のパブリックDNSサーバーを用いた検証を再度単独で実行します。
   - Google Public DNS (`8.8.8.8`)
   - Cloudflare DNS (`1.1.1.1`)
   これにより、DNSキャッシュの浸透状況や、GeoIP制限（海外からの名前解決失敗）、スプリットホライズン（内部/外部でのレコード不一致）などを検出し、MPICの要件を満たすかどうかを自動判定します。

8. **発行方式（CSR / ACME）による違いの分類**
   検出した不備ごとに、それが **CSRによる申請** と **ACMEによる発行** のそれぞれでどう効いてくるかを `[CSR申請の場合]` / `[ACME発行の場合]`（両者で挙動が同じ場合は `[CSR申請/ACME発行に共通]`）のラベル付きで出力します。
   判定結果の末尾には **【発行方式別の見通し】** として方式ごとの可否（✅ / ⚠️ / ❌）と、方式差をまとめた凡例が表示されます。

9. **UPKI申請TSVの読み込み（`-f`）**
   FQDNの代わりにUPKIの申請TSVファイルを指定すると、各申請行の **利用管理者FQDN（11列目）** と **dNSName（13列目）** に書かれたホスト名をすべて確認し、最後に **【申請行ごとのまとめ】** を表示します。
   - 対象の申請種別: サーバ証明書 発行申請・更新申請、ACME利用情報 作成申請・更新申請（いずれも11列目・13列目の位置は共通）
   - 11列目のFQDNは13列目に書かれていなくてもUPKI側で自動付与されるため、両方を確認対象にします。
   - 同じホスト名が複数の行や同じ行に出てきても（大文字小文字の違いを含む）、確認は1回だけ行います。
   - 1枚の証明書（ACMEでは1回のorder）に含まれるホスト名が1つでも発行できなければ申請全体が失敗するため、行の判定は最も悪いホスト名の結果に合わせます。
   - 失効申請など11列目・13列目が空の行は対象外として読み飛ばします。`dNSName=` の付いていない要素、ワイルドカード、末尾カンマ、9個以上の指定など、UPKIで申請エラーになる記述は警告します。
   - TSVはUPKIの仕様どおり Shift-JIS / CR+LF のままで読み込めます（変換は不要です）。

10. **まとめだけの表示（`-q`）**
    `-q` を付けると、上位ドメインへの遡りやパブリックDNSごとの確認ログを省き、判定のまとめだけを表示します。ホスト名の多いTSVを確認するときに便利です。

11. **権威DNSサーバーへの直接問い合わせ**
    パブリックDNS（8.8.8.8 / 1.1.1.1）はキャッシュを持ち、国内の拠点から応答するため、権威DNSサーバー間の不一致や一部のサーバーの無応答は見えません。そこで、対象FQDNが属するゾーンの権威DNSサーバー（eTLD+1まで遡って最初に見つかったNSレコード）を特定し、各サーバーのIPv4アドレスへ再帰なし（`+norecurse`）で直接問い合わせます。
    - **サーバー間で応答（ステータス・CAA・CNAME）が食い違う場合は ❌** とします。CAのDNS観測点はどの権威DNSサーバーに問い合わせるかが毎回異なるため、観測点ごとに結果が揃わず、CSR / ACME どちらの方式でも発行が抑制されます。
    - 次の場合は、必ず失敗するとは限らないため、判定は変えずに **【注意】** として表示します（`-q` やTSVのまとめでは「注意:」「(注意あり)」と表示）。
      - SOAシリアルだけが一致しない（ゾーンの同期の遅れ）
      - 一部の権威DNSサーバーが応答しない・問い合わせを拒否する（REFUSED など）
      - どの権威DNSサーバーにも直接問い合わせできない（この端末からの53番ポートの制限など）
      - NSレコードを特定できない、IPv4アドレスのない権威DNSサーバーがある
    - IPv6での到達性は、確認する側の端末にIPv6がないと誤って失敗するため確認していません。

12. **DNSSECの確認**
    SC-085v2 により、2026-03-15 以降、CAはDNSSECの検証が必須です。署名に不備のあるドメインは、検証を行うパブリックDNS（8.8.8.8 / 1.1.1.1）で SERVFAIL になり、CAもCAAやDCVの確認ができないため、CSR / ACME どちらの方式でも発行できません。
    - パブリックDNSが SERVFAIL を返したときは、`+cd` を付けて問い合わせ直します。**`+cd` で解決できれば DNSSECの検証失敗** と判断し、海外からのアクセス制限（GeoIPブロッキング）ではなく、署名の期限切れ、親ゾーンのDSレコードとDNSKEYの不一致、鍵の更新（ロールオーバー）の失敗などを原因として表示します。
    - `+cd` でも解決できない場合は、従来どおりGeoIPブロッキングなどを原因として推測します。
    - 権威DNSサーバーの確認では、親ゾーンにDSレコードがあるか（＝ゾーンが署名されているか）も表示します。署名がないこと自体は問題ではありません。
    - どの段階で検証に失敗しているかの詳細は、DNSViz などの診断ツールで確認してください。

13. **ACME向けの事前確認**
    UPKIのACMEで使える検証方式（**dns-01 / http-01**。tls-alpn-01 はUPKIでは使えません）が、DNSの面で使えるかを確認します。CAはインターネット上から確認するため、パブリックDNS（8.8.8.8 / 1.1.1.1）に問い合わせます。

    | 検証方式 | 確認すること | 使えないと判定する場合 | 【注意】として表示する場合 |
    |---|---|---|---|
    | dns-01 | `_acme-challenge.<FQDN>` の名前解決（TXT と、委任用のCNAME） | 名前解決に失敗する（SERVFAILなど） | CNAMEの参照先（acme-dns などの委任先）が存在しない |
    | http-01 | FQDN の A / AAAA レコード | A / AAAA がない、またはすべてプライベートアドレス | プライベートアドレスが混ざっている |
    | tls-alpn-01 | ― | UPKIのACMEでは使えません | ― |

    - **使える方式が1つでもあれば ACME は ✅** のままで、「発行方式別の見通し」に使える方式を表示します。**どの方式も使えなければ ACME は ❌** です。
    - `--acme-method dns-01` / `--acme-method http-01` で使う方式を指定すると、その方式だけで判定します。【注意】も、指定した方式に関するものだけを表示します。
    - AAAAレコードがある場合は、詳細表示で「(参考)」として、IPv6でも80番ポートで応答するか確認するよう表示します（CAはIPv6で接続することがあるため）。IPv6に対応したドメインでは普通のことなので、【注意】にはせず、終了コードにも影響しません。
    - `_acme-challenge.<FQDN>` が今は存在しない（NXDOMAIN）のは正常です。TXTレコードはACMEクライアントが検証のたびに設置します。残っている古いTXTレコードは参考として表示するだけです。
    - CDNなどではDNSサーバーごとに違うアドレスを返すのが普通なので、アドレスはDNSサーバー間で比べません。
    - プライベートアドレスとして扱う範囲: IPv4 は `0/8`・`10/8`・`100.64/10`・`127/8`・`169.254/16`・`172.16/12`・`192.168/16`、IPv6 は `::`・`::1`・`fc00::/7`・`fe80::/10`
    - 80番ポートへの実際の接続は確認していません（この端末からの接続結果は、海外にあるCAの観測点からの到達性と一致しないため）。

14. **終了コード**
    確認結果に応じて 0〜3 の終了コードを返します（後述の「終了コード」を参照）。cron や CI での定期的な監視に使えます。

## 発行方式（CSR / ACME）による違い

### MPIC は ACME 固有の仕組みではありません

MPIC（Multi-Perspective Issuance Corroboration、BR 3.2.2.9）は **BR 3.2.2.4 のすべての DCV 方式に適用**されます。CAAレコードの参照も MPIC の対象です（CAAルックアップに対する BGP ハイジャックで発行制限を迂回されるのを防ぐため）。
したがってセコムが DNS/HTTP で DCV を行う限り、**CSR経由の発行でも MPIC はかかっています**。ACME だけの話に見えるのは、MPIC が走るタイミングが違うためです。

MPIC のリモート観測点の要件は段階的に引き上げられています。

| 時期 | 要件 |
|---|---|
| 2025-03-15 | 2リモート観測点（監視モード。結果に関わらず発行可） |
| 2025-09-15 | quorum 要件の遵守が必須に（不足で発行停止） |
| 2026-03-15 | 3リモート観測点 |
| **2026-06-15** | **4リモート観測点（現行。うち3点以上が主観測点と一致し、かつ2つ以上のRIR地域からの観測が必要）** |
| 2026-12-15 | 5リモート観測点 |

### 方式で挙動が分かれるのは「対象FQDNが NXDOMAIN」のケース

BR の DCV は、申請された FQDN そのものではなく、**そこから左側のラベルを削って導出した ADN（Authorization Domain Name）に対する管理権限**を確認する設計です（Ballot SC-101v2 が明文化）。検証データの再利用も ADN 単位で機能します。

- **CSR申請** … `example.ac.jp` に対して一度 DCV を済ませてあれば、`nonexistent.example.ac.jp` のような NXDOMAIN の FQDN でも、**CAAチェックさえ通れば発行され得ます**。
  「上位まで遡ってCAAが適切なら発行できた」という従来の観測は正確ですが、その理由はCAAではなく、**ADNレベルで完了済みのDCVが再利用されていた**ことにあります。
- **ACME発行** … RFC 8555 の dns-01 はチャレンジを identifier そのものの `_acme-challenge.<FQDN>` に置くと定義されており、http-01 / tls-alpn-01 は当該FQDNの A/AAAA 解決が前提です。つまり **ACMEでは実質的に ADN が申請FQDNに固定されます**。さらに RFC 8020 の解釈下では FQDN が NXDOMAIN ならその配下も存在しないため `_acme-challenge` も引けません。
  ACMEで発行が抑制されるのは MPIC のせいというより、**この ADN 固定の帰結**です。

### CAA と DCV は別レイヤです

| | 役割 | 確認タイミング | 上位への遡り |
|---|---|---|---|
| **CAA**（RFC 8659） | どのCAが発行してよいかの許可リスト | 発行の8時間以内（ACMEでは finalize 時） | 仕様どおりの正常動作。NXDOMAINは障害にならない |
| **DCV**（BR 3.2.2.4） | 申請者が本当にそのドメインを管理しているかの証明 | 方式による（下表） | ADN単位で実施・再利用される |

### エラーの現れ方と気付きやすさ

| | CSRによる申請 | ACMEによる発行 |
|---|---|---|
| 検証のタイミング | UPKI(NII)へ申請した後、CA側でまとめて実施 | order（証明書要求）ごとにその都度実施 |
| エラーの現れ方 | 「**エラー338**」としてUPKI側に記録され、申請が発行に至らない | **エラー338は発生しない**。ACMEクライアント側のエラーとして返る |
| 対象FQDNがNXDOMAIN | 上位ADNでDCV済み＋CAA適切なら発行され得る | 発行できない |
| 気付きやすさ | 申請が通らないため必ず気付く | 自動更新では失敗が表面化しにくく、**気付かないまま証明書が期限切れになる恐れがある** |

### DCV 再利用期間の短縮（CSRフローに直接効きます）

SC-081v3 により、証明書有効期間と DCV 再利用期間が段階的に短縮されます。

| 時期 | 証明書有効期間 | DCV再利用期間 |
|---|---|---|
| （従来） | 398日 | 398日 |
| **2026-03-15** | **200日** | **200日** |
| 2027-03-15 | 100日 | 100日 |
| 2029-03-15 | 47日 | 10日 |

CSRフローで「機関ドメインを一度確認して1年使い回す」運用は **2026-03-15 以降すでに成立していません**。2029年に10日になった時点で、CSRフローは申請のたびに実質再検証が必要になります。

### その他の関連する制度変更

- **SC-090**（2026-01-14採択）… メール／電話ベースのDCV方式を、SC-085 の発効日（2026-03-15）以降 非推奨に。
- **SC-085v2**（2026-03-15）… DNSSEC 検証が必須に。
- **SC-098**（2026-06-16に BR v2.2.8 へ反映、発効予定 2027-03-15）… RFC 8657 の CAA パラメータ（`accounturi` / `validationmethods`）の処理。
- **SC-101v2**（適用期限 2026-11-15）… 新しい ADN 導出アルゴリズム。**CNAME追跡とラベル削除の順序が厳格化**されるため、CDN配下や CNAME を多用する機関で挙動が変わる可能性があります。
  （従来の解釈では、CNAME を1つ以上たどって得たFQDNをADNとして使えると読め、CNAME先の運用者が任意のサブドメインの証明書を発行させられる余地がありました）

## 仕組みと動作要件

### 動作要件
- OS: Linux / macOS などのUNIX系OS（`readlink -f` は使わないため、macOS 12.2 以前でも動作します）
- 必須コマンド: `bash`, `dig` (bind-utils/dnsutils), `curl`, `awk`, `grep`, `sed`
- ネットワーク接続: DNSクエリ（ポート53）、およびPSLのダウンロード（初回と、30日ごとの取り直し）のためのインターネット接続（HTTPS）

### Public Suffix List (PSL) について
ドメインは単純に「最後のドットから数個」だけで頂点を判断することができません（例: `.com` は1つ前が頂点だが、`.co.jp` や `.ac.jp` は2つ前が頂点になるため）。
本スクリプトは正確な判定を行うため、スクリプトと同じディレクトリに `public_suffix_list.dat` というリストファイルを要求します。存在しない場合は `curl` で自動的にダウンロードして使用します。

PSLには新しい公開サフィックスが随時追加されるため、古いリストのままだと eTLD+1 を誤る可能性があります。そこで次のように更新します。
- リストが **30日より古ければ、実行時に自動で取り直します**。取り直しに失敗した場合（ネットワークの制限など）は、手元のリストのまま確認を続けます。
- `--update-psl` を付けると、日数にかかわらず取り直します。FQDNやTSVを指定せずに `--update-psl` だけを付けた場合は、取り直したところで終了します（失敗した場合の終了コードは 3）。
- 取得した内容は、PSLであること（`===BEGIN ICANN DOMAINS===` の行があること）を確かめてから置き換えます。エラーページなどで上書きされることはありません。
- 取得や更新のお知らせは標準エラー出力に出すため、`-q` のまとめの出力には混ざりません。

環境変数 `CHECK_MPIC_PSL_FILE` にファイルのパスを指定すると、別の場所にあるリストを使えます（テストではこれで最小限のリストに差し替えています）。指定したファイルは、`--update-psl` を付けない限り自動では取り直しません。
同じように、環境変数 `CHECK_MPIC_TODAY`（`YYYY-MM-DD` 形式）で今日の日付を差し替えられます。CAAのパラメータの施行日（2027-03-15）より前と後の動作を確かめるときに使います。

## 使用方法

### 1. 実行権限の付与（初回のみ）
ターミナルを開き、スクリプトに対して実行権限を付与します。
```bash
chmod +x check_mpic.sh
```

### 2. スクリプトの実行
引数として、確認したい対象のFQDN、または `-f` でUPKIの申請TSVファイルを指定して実行します。
FQDNは末尾のドットを取り除き、小文字にそろえてから確認します。URL（`https://...`）など、ホスト名の形式でないものはエラーになります。
```bash
./check_mpic.sh [-q] <FQDN>
./check_mpic.sh [-q] -f <申請TSVファイル>
```

| オプション | 内容 |
|---|---|
| `-f`, `--tsv FILE` | UPKIの申請TSV（サーバ証明書 発行/更新、ACME利用情報 作成/更新）を読み込み、11列目・13列目のホスト名をすべて確認します |
| `-q`, `--quiet` | 個別の確認ログを省略し、判定のまとめだけを表示します |
| `--acme-method METHOD` | ACMEで使う検証方式（`dns-01` / `http-01`）を指定し、その方式で発行できるかを判定します。指定しなければ、どちらかの方式で発行できればACMEを可とします（`tls-alpn-01` はUPKIでは使えないためエラーになります） |
| `--update-psl` | Public Suffix List を取り直します。FQDNやTSVを指定しなければ、取り直すだけで終了します |
| `-h`, `--help` | 使い方を表示します |

#### 終了コード
cron や CI での定期的な監視に使えるよう、監視ツール（Nagios など）の慣習に合わせた終了コードを返します。
TSVを読み込んだ場合や `-q` を付けた場合も同じです。

| 終了コード | 意味 |
|---|---|
| `0` | 確認したすべてのホスト名で問題なし（CSR / ACME とも ✅、【注意】なし） |
| `1` | ⚠️（条件付き）の判定、または【注意】がある |
| `2` | ❌（発行できない）判定がある。CSR / ACME のどちらか一方でも ❌ なら 2 になります |
| `3` | 引数の誤りやファイルが読めないなどのエラーで、確認できなかった |

```bash
./check_mpic.sh -q -f server_issue.tsv > result.txt || echo "要確認 (終了コード: $?)"
```

#### 実行例
```bash
./check_mpic.sh certs.nii.ac.jp
./check_mpic.sh -q -f server_issue.tsv
```

#### 判定にパスしない場合の出力例
不備が検出された場合は、原因ごとに `[CSR申請の場合]` / `[ACME発行の場合]` の影響が併記され、末尾に方式別の見通しが表示されます。
以下は対象FQDNが NXDOMAIN で、**ACMEでは発行できないが CSR では上位ADN次第**というケースの例です。

```text
==================================================
【MPIC判定結果】 (Multi-Perspective Issuance Corroboration)
==================================================
判定結果: ❌ パスしない（エラーになる）可能性が高いです。
以下の原因が考えられます：
・すべてのDNSサーバーでNXDOMAIN（名前解決失敗）となりました。
  [ACME発行の場合] 発行できません。dns-01のチャレンジは _acme-challenge.nonexistent-test-zzz.nii.ac.jp に置く必要がありますが、
                   RFC 8020によりNXDOMAINのFQDN配下の名前も存在しないため参照できません。http-01/tls-alpn-01もA/AAAAが必要です。
  [CSR申請の場合]  直ちに発行不可とは限りません。DCVは対象FQDNではなくADN(上位ドメイン)に対して行われるため、
                   上位ADNでDCV済みかつCAAが適切であれば、対象FQDNがNXDOMAINでも発行され得ます。
                   ただしDCVの再利用可能期間は2026-03-15以降200日に短縮されており(2027-03-15に100日、2029-03-15に10日)、
                   再検証のタイミングでは上位ADN側が解決できる必要があります。

--------------------------------------------------
【発行方式別の見通し】
  CSR申請  : ⚠️  上位ADNでDCV済み(200日以内)かつCAAが適切であれば発行され得ます。UPKI/CAへの確認を推奨します。
  ACME発行 : ❌ 発行できません。
--------------------------------------------------

※【発行方式(CSR / ACME)による違い】
  ・MPICはACME固有の仕組みではなく、BR 3.2.2.4のすべてのDCV方式(CAAの参照を含む)に適用されます。
    そのためCAAの不備・観測点間の不一致・SERVFAILは、CSR/ACMEどちらの方式でも発行を抑制します。
  ・両者で挙動が分かれるのは「対象FQDN自体が引けない(NXDOMAIN)」ケースです。

    自動更新では失敗が表面化しにくいため、気付かないまま証明書が期限切れになる恐れがあります。
  ・DCVの再利用可能期間は2026-03-15以降200日(2027-03-15に100日、2029-03-15に10日)に短縮されており、
    CSR方式で上位ADNのDCV結果を長期間使い回す運用は成立しなくなります。
```

## テスト

`tests/run_tests.sh` で、関数の単体テストとスクリプト全体の結合テストを実行できます。
本物の `dig` の代わりに模擬の `dig`（`tests/mock/dig`）を使うため、**ネットワークに接続せず**、いつでも同じ結果になります。

```bash
tests/run_tests.sh
```

| ファイル | 内容 |
|---|---|
| `tests/run_tests.sh` | テストの本体。失敗が1件でもあれば終了コード 1 を返す |
| `tests/mock/dig` | 模擬の `dig`。`check_mpic.sh` が使う呼び出し方だけに対応し、ゾーンファイルから応答を返す |
| `tests/mock/curl` | 模擬の `curl`。PSLの取得の成功・失敗・PSLでない内容を、ネットワークに接続せずに再現する |
| `tests/fixtures/zone.txt` | 模擬DNSのゾーン。CAAの配置、CNAME、NXDOMAIN、DNS拠点ごとの応答の違い（SERVFAIL・タイムアウト・不一致）、権威DNSサーバーごとの応答の違い（不一致・SOAシリアル・無応答・拒否）、DNSSECの署名の有無と検証失敗、CAAのパラメータ（accounturi・validationmethods）、ACME向けの事前確認（_acme-challenge・プライベートアドレス・AAAA）を定義 |
| `tests/fixtures/public_suffix_list.dat` | テスト用の最小限の Public Suffix List |

新しい判定ケースを追加するときは、`zone.txt` にレコードを足し、`run_tests.sh` に期待する判定を書きます。
ゾーンファイルの書式は `tests/mock/dig` の冒頭のコメントを参照してください。

`check_mpic.sh` は `source` しても実行されない（関数の定義だけが読み込まれる）ため、テストから個々の関数を直接呼び出せます。
